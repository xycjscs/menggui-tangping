- **虚拟时钟 s.time**：波次排期全部基于虚拟秒，真实墙钟只用于广告冷却/存档
  - 这是第一个重大设计决策：战斗在任何速度下确定、可测试
- **数值成长曲线**（CURVE 对象集中管理，方便调参）：
  - 床产量 1.55^n > 炮塔 DPS 1.35^n > 鬼血量 1.22^n → 玩家永远追得上

- **战斗模型**：按"实际击杀时间"结算门受击（鬼死即停），避免高波次同帧秒杀
- **失败流程**：门破 → defeated 冻结 → 看广告复活(门回50%,每局限1次,60s冷却) / 接受失败(灵魂x0.3,床等级减半,门炮重置)

## 2026-08-18 v0.3.0 2D 可视化战场（俯视战棋，移动怪物）

### 背景
v0.2 是纯数值/文字 UI（顶栏数字 + 卡片按钮），用户反馈"变成文字游戏了"，要求**有画面、怪物会动、2D 战棋风格**。

### 设计决策
1. **渲染层与核心彻底解耦**：新增 `js/battle/battleView.js`（环境无关，只读 core 状态、绝不改数值）。
   Web 和小程序共用同一份，零分叉；核心 `gameCore.js` **一行未改**，146 测试全绿保证数值不变。
2. **对账式可视化**：core 每秒把 DPS 按 id 打到 `s.ghosts` 并逐只结算死亡。渲染层每帧用
   `key = wave*100+id` 对账——新增 id 生成入场幽灵、hp 下降触发受击闪白+伤害飘字、id 消失触发死亡动画。
   画面"打得热闹"，但胜负/血量/奖励 100% 由 core 决定（**视觉不反噬数值**）。
3. **俯视战棋布局**（设计空间 750×430 等比适配）：左 33% 宿舍（6 床 2×3 + 祭坛 + 英雄列）、中砖墙大门+炮塔、
   右 55% 走廊。幽灵从右侧阴影**逐个错峰走出 → 列阵推进 → 原地突刺攻击门**。
4. **战棋战斗反馈**：炮塔旋转追踪 + 曳光弹道 + 炮口焰；Boss 1.7 倍体型 + 红圈光环 + BOSS 标签；
   门受击**震屏闪红**（幅度与实际掉血成正比）；死亡爆裂粒子 + 灵魂/金币掉落飘字；床 Zzz/金币粒子、祭坛灵魂环绕。

### 踩坑记录（v0.3 特有）
1. **幽灵 key 缺波次前缀**：`makeSprite` 里 `key: g.id` 漏掉 `wave*100+`，跨波次复用 id 导致对账错乱 → 改为 `key: wave*100+id` 透传。
2. **全局名大小写**：UMD 导出 `window.BattleView`，Web 端误写 `window.battleView` → 渲染循环每帧抛错、canvas 空白。
3. **CSS 覆盖顺序**：隐藏旧文字横幅的 `display:none` 规则写在原 `.wave-banner`（`display:flex`）之前被覆盖 → 移到之后加 `!important`。
4. **Boss 血条被 HUD 遮挡**：阵型顶行 y 太靠上 → `ghostSlot` 整体下移 0.12 格 + 血条/标签 `y = max(y, hudH+9)` 钳位。
5. **测试环境 `beforeunload` 自动存档**：navigate 时旧页面存回 localStorage，"新档"其实带旧状态 → 改用 `?fresh=1` 强制清档。

### 测试与验证
- 新增 16 条战场渲染层无头断言（mock 2d ctx）：入场/列阵/死亡/清理/Boss/门破/NaN 防护 → **146/146 全绿**

- 包体积 ~588KB（含 web），远低于 4MB 单包上限

## 2026-08-18 v0.4.0 三屏游戏流程 + 点触菜单 + 关卡制

### 背景
用户反馈："应该是一些长效设置、奖励、关卡选择的首页，和进入游戏的交互页。游戏中所有的菜单和升级等应该是触摸了对应游戏内容而弹出菜单，而不是把菜单全都放在下面。**游戏画面才是主要展示**"。
→ v0.3 虽然有了战场画面，但升级菜单还堆在战场下方，首页/进入页/关卡制也缺失。这次做完整的游戏 UX 流程重构。

### 设计决策
1. **三屏流程**（单页内 screen 切换，Web 与小程序同架构）：
   - **首页**：关卡选择（8 关，通关解锁下一关，星级评价）+ 长效钱包（跨关卡累计金币/灵魂）+ 每日福利 + 广告福利。
   - **进入页**：关卡详情 + 初始配置 + 入场支援三选一（免费：金币/灵魂/大门+2级）+ 精锐支援（钱包金币付费，开局额外资源）。
   - **游戏屏**：战场 canvas 为主角，顶部只留 退出/关卡进度/本局资源。
2. **点触上下文菜单（核心）**：战场 canvas 加 `bindtap`/click → `battleView.hitTest(x,y)` 命中检测
   → 返回点中的元素（bed/door/turret/altar/hero + index）→ 在元素旁弹出菜单（升级/解锁/招募/献祭）。
   点空白处收起。菜单贴元素定位，不遮挡战场。**升级操作全部从 canvas 元素触发，不再堆底部列表。**
3. **关卡制 = 自包含波次挑战**：每关有初始资源（床/门/炮塔/祭坛/英雄）+ "清除 N 波"胜利目标。
   通关 → 结算进钱包 + 星级（未复活 3 星 / 1 次复活 2 星 / 多次 1 星）；门破 → 看广告复活（每局 1 次）或认输（本局作废）。
   过关解锁下一关；每关可重复挑战刷更高星。
4. **关卡数据独立模块 `js/levels.js`**（UMD，纯数据+纯函数，Node 可测）：8 关配置 + 解锁/星级/支援/精锐辅助函数。
   **关卡系统是控制器层概念，核心 `gameCore.js` 数值零改动**（newGame 再按关卡配置覆盖即可开局）。
5. **长效数据与单局存档分离**：钱包/关卡进度/设置/每日福利日期存 `menggui_tangping_meta_v1`；
   单局 core 状态不跨关持久化（每关从 newGame 重建）。

### 踩坑记录（v0.4 特有）
1. **bootstrap 异步加载竞态**：Web `bootstrap.js` 是 `fetch` 异步加载 core/number，派发 `core-modules-ready` 事件。
   `game.js` 的 `init()` 若不等该事件直接跑，`window.num` 未定义 → `bindModules` 抛错、首页关卡网格空白。
   修复：`boot()` 监听 `core-modules-ready` 再 init，加 8s 兜底报错。
2. **精锐支援状态被重置**：`startLevel` 里 `eliteUsed=false` 重置发生在读取"是否启用"之后 → 精锐永不生效。
   修复：先 `wantElite = eliteUsed` 再重置，用 wantElite 决定扣钱包+加资源。
3. **点触菜单定位**：canvas 设计空间(750×430) → 屏幕 px 需按 `getBoundingClientRect`/canvas 实际尺寸换算，
   并做边界钳位（不超出 stage）。Web 用 `positionTapMenu`，小程序用 `battle.menuPos`。

### 测试与验证
- 新增 23 条断言（section 19）：关卡数据/解锁/星级/支援/精锐 + hitTest 命中检测（门/炮塔/祭坛/英雄/床/空白/层级）→ **169/169 全绿**
- Camofox 真机实测：首页(8关+7锁) ✓ / 进入页(关卡+支援) ✓ / 游戏屏战场渲染 ✓ / 点门/床弹菜单 ✓ / 升级 ✓ / 5波通关→3星结算→钱包+解锁第2关 ✓
- Web 与小程序共用 `js/levels.js` + `js/battle/battleView.js`（含 hitTest），核心数值零改动
